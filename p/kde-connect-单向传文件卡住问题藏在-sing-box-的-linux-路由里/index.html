KDE Connect 单向传文件卡住，问题藏在 sing-box 的 Linux 路由里

2026-09-20

两台电脑明明已经配对，Windows 往 NixOS 传文件正常，反过来却一直卡在发送页面。最开始我以为是 Windows 防火墙，后来抓包才发现，问题其实出在 NixOS 上的 sing-box 路由。

现象有点反直觉

NixOS 发起分享后，Windows 会反过来连接 NixOS 临时监听的端口来取文件。抓包能看到 Windows 发来的 SYN，但 NixOS 没有从无线网卡回 SYN-ACK。

查路由时原因就很明显了：

172.26.92.186 via 172.19.0.2 dev singtun0 table 2022

回包被策略路由送进了 singtun0，连接自然卡在握手阶段。

配置里虽然已经有 ip_is_private: true -> direct，但这条规则要等流量进入 sing-box 后才会生效。它决定的是 sing-box 选哪个出站，并不能替内核修正这条连接的回程路由。也正因为如此，“私有地址会走 direct”并不等于“内核一定从局域网网卡直连”。

修复

原来的 TUN 入站已经启用了 auto_route，再加一行 auto_redirect：

{
  "type": "tun",
  "auto_route": true,
  "auto_redirect": true,
  "strict_route": true
}

然后重建 NixOS：

sudo nixos-rebuild switch --flake ~/nixos#x250

auto_redirect 会在 Linux 上配合 nftables 和连接跟踪处理流量。启用后，同一连接的回复方向不再被 TUN 的兜底策略路由抢走。此时再查 Windows 地址，已经回到无线网卡直连：

172.26.92.186 dev wlp3s0 src 172.26.11.104

验证

再次从 NixOS 分享测试文件，抓包里这次完整出现了：

Windows -> NixOS:1739  SYN
NixOS:1739 -> Windows  SYN-ACK
Windows -> NixOS       ACK
双向 TLS 数据
双方 FIN

从 SYN 到传输结束不到 0.4 秒，文件发送恢复正常。

我还保留了 EasyTier 网段的排除项：

"route_exclude_address": [
  "10.100.100.0/24"
]

改完后 EasyTier 仍然走 easytier0，连通性也正常。这次问题说到底不是 KDE Connect 坏了，也不是私有地址规则没匹配，而是 Linux 内核在流量进入 sing-box 之前，就先替回包选错了路。

其他平台要不要开 auto_redirect？

后来我又翻了下官方的 TUN 文档，这个选项其实不能到处照抄。Linux 上是完整实现，会配合 nftables 和策略路由工作，所以官方建议和 auto_route 一起开。Windows 和 iOS 没有这套机制，不需要加。

Android 稍微特殊一点。官方确实说它也能用，但只是借助 root 和 iptables 做简单的 IPv4 TCP 重定向，不包括 IPv6 和 UDP，跟 Linux 版不是一回事。官方 Android 客户端默认也是关闭的，开启时会要求 root。

所以普通 Android 手机继续用 auto_route 就行。只有手机已经 root，而且刚好遇到 IPv4 TCP 或局域网入站连接的问题，才值得打开做一次对照测试。
